# Jump to Reach the Sky — BACKEND (game server)

Frontend (3D client) lives at `../Jump-to-reach-the-sky` (its `src/net.js` is the other half of this contract). Colyseus + Mongo. The server was ported from Bowling Roll; everything of the old boat game (boats, engines, pets, races, spin wheel) is gone; presence is new (see below).

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp })`). **Room size = the number of bases in the hub**: `ROOM_MAX_CLIENTS` (`src/constants.ts`) = the client's `HUB.plots.count` (6). Every player gets a free base, `seat` (0..5, west -> east, the roster's `PlayerState.seat`), and the client builds that plot as its own (`HUB.plots.local`, spawn and the Home teleport follow it). A seat is freed when its player leaves for good (a dropped connection keeps it for `RECONNECT_SECONDS`). A seventh player is refused and the Legion matchmaker opens another pod.
- Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- **Identity (`src/auth.ts`)**: the server never trusts a user id from the client. The client sends its Bloxity token (`Legion.SDK.auth.getToken()`) as `token` in the join options and in `identify`; the server asks Bloxity (`POST {BLOXITY_API_URL or https://api.bloxity.io}/v1/auth/game-token/verify`, Bearer token, body `{ gameSlug }`) and only the returned `user._id` is an account id (username from Bloxity too). A missing / refused token is a guest, with NO fallback to a client id. Only a local development server (`NODE_ENV` not `production`, or `ALLOW_CLIENT_IDS=true`) accepts the client's own `dev-...` id. Tests stub the call with `__setVerifierForTest`. Guest progress carry-over (`carriedFrom`) is not used (guest progress stays on the device).
- **Bloxity leaderboards (`src/reporter.ts`)**: on Bloxity hosting the server reports scores (`POST {BLOXITY_API_URL}/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report`, Bearer `BLOXITY_REPORT_TOKEN`): boards `LEADERBOARDS` in `constants.ts` (ids `total-earned`, `jump-power`, `rebirths`, fed by the saved fields; the client declares the same with `leaderboard.define`), only for Bloxity-verified accounts as `legion_<id>` (a `#m...` suffix stripped), changed scores only, batched every 15 s (<= 200 per call, also when a player leaves), capped at `Number.MAX_SAFE_INTEGER`. The board declarations ride on the first report. No token / game id (local dev) = nothing is sent. The room reporter for Open Rooms is automatic on Bloxity-hosted servers.
- Messages client -> server: `sync` (sent once the client's handlers exist and after every reconnect; messages the server sends from `onJoin` would be dropped, so the first answer waits for it), `saveProgress` (the whole snapshot, throttled client-side), `identify` (`{ token, userId, username, pfp }` after a sign-in/out mid-session), `claimDaily` (`{ all?: boolean }`), `pose` and `look` (presence, below).
- Server -> client (private): `progress` / `noProgress` / `serverError`, each with `seat` and `serverTime` (the saved doc sanitized / a new account, guest or no database: the client keeps its fresh state and saves it / the save could not be read: saving stays off so it is never overwritten); `daily`; `dailyResult`; `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted. Roster (`PlayerState`): `username`, `signedIn`, `pfp`, `seat` and the presence fields below.
- **Presence (`src/presence.ts`, constants `POSE_*` / `LOOK_*` / `OUTFIT_MAX` / `STACK_SHOWN_MAX` / `BASE_SHOWN_MAX`)**: how players see each other (client `src/presence.js` sends, `src/remotePlayers.js` draws). `pose` { x, y, z, yaw, speed, grounded, carrying } (~10/s) -> `sanitizePose`: finite numbers only (anything else is dropped whole), x / z within `POSE_XZ_MAX`, y within `POSE_Y_MIN..POSE_Y_MAX`, yaw wrapped to -PI..PI, speed `0..POSE_SPEED_MAX`, carrying `0..CARRY_MAX`; at most one per `POSE_MIN_INTERVAL_MS` per player (`RateGate`, extras dropped). `look` { item, outfit, stack[], slots[], unlocked } (on change) -> `sanitizeLook`: `item` an id, `outfit` the Bloxity outfit key kept only if it is at most `OUTFIT_MAX` chars of `[A-Za-z0-9_.,:;|~=+-]` (no `/ ? # %` or spaces, so never a URL, otherwise ""), `stack` the carried brainrots (at most `STACK_SHOWN_MAX`) and `slots` the base pedestals (at most `BASE_SHOWN_MAX`, empty = `-`) encoded as `species:variant,...` from ids only (`ID_PATTERN`), `unlocked` bought pedestals; at most one per `LOOK_MIN_INTERVAL_MS`. Both land on the sender's own `PlayerState` (`posed` turns true on the first pose; until then x / y / z mean nothing), which every client reads through the normal schema sync; nothing else is relayed, no cross-player messages. The base pedestals come from the client's `look`, not from saves, so guests' bases show too. Tests: `test/Presence.test.ts`.
- Saved progress shape (`PlayerDoc` in `src/db.ts`, client `src/game/state.js` `SAVED` + `t` -> `lastSeen`): `money`, `totalEarned`, `jumpPower`, `rebirths`, `slotsUnlocked`, `slots[] { species, variant, bank?, income? } | null` (by pedestal), `pads[]`, `skips[]`, `bestZone`, `index { species: { variant: true } }`, `perks { id: true }`, `boosts { id: seconds }`, `smartJump`, `carried[]`, `speed`, `carryMax`, `luckyJumps`, `items { id: true }` + `equipped` (must be owned), `luckyBlocks { tier: count }` (unopened Lucky Blocks, whole counts <= `LUCKY_BLOCKS_MAX`, at most `LUCKY_TIERS_MAX` tiers), `crystals` (Jump Crystals picked up, <= `CRYSTALS_MAX`), `fusion { species, from, to, at, ms } | null` (the Fusion Machine job: ids, `ms` <= `FUSION_MS_MAX`, `at` no later than now + `FUSION_MS_MAX`; null = idle, malformed = ignored), `ascended { perkId: level }` (Ascended Shop perks, whole levels <= `ASCENDED_LEVEL_MAX`, zeros dropped), `baseLevel` (<= `ZONES_MAX`), `baseBuild { level, at, ms } | null` (a Base Level under construction: `ms` <= `BASE_BUILD_MS_MAX`, `at` no later than now + that), `dailyPass`, `dailyMilestones { day: true }`, `lastSeen` (offline income counts from it). Money and Jump Power go up to ~1e41, bound `NUMBER_MAX` = 1e100. Ids match `ID_PATTERN`.
- Daily Rewards (`src/daily.ts`, constants `DAILY_*`): server-authoritative on the server clock. One claim per `DAILY_COOLDOWN_MS` (20 h), a gap over `DAILY_STREAK_BREAK_MS` (48 h) restarts at Day 1 (and clears `dailyMilestones`), the cycle is `DAILY_CYCLE` = 7 days. The Claim All Pass (`dailyPass`, saved by the client) lets mid-week days be claimed without waiting and `{ all: true }` claims the rest of the week. Doc fields `dailyDay` (streak days claimed) and `dailyAt` (ms of the last claim) are written only by the server, never by `saveProgress`. `daily` { day, at, cooldownMs, serverTime, reset } is sent after the load; `claimDaily` answers `dailyResult` { ok, count, reason?: "loading" | "locked" | "save", reset, day, at, cooldownMs, serverTime } (ok only once stored). Guests / no-DB sessions keep theirs in memory for the connection.
- Leaderboards (`src/leaderboard.ts`): the hub's two boards (client `hub/leaders.js`). Top `LEADERBOARD_SIZE` (16) saved players by each of `LEADERBOARD_STATS` (`totalEarned`, `jumpPower`), read into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS`. `connectDb` creates a descending index per stat.
- `src/constants.ts` bounds must cover the client's `src/config.js` (list sizes, ids). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev; docs: hosting.bloxity.io/docs), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (docs.bloxity.io: send `roomSize`, never `seatCap`; hosting.bloxity.io says the capacity should equal `maxClients`, which it does). Clients must reach the server through the matchmaker (`Legion.SDK.net.resolveEndpoint`), never the host URL. Needs repo var/secret `LEGION_GAME_ID` (= the client's `GAME_SLUG`) and secret `LEGION_DEPLOY_TOKEN`.
